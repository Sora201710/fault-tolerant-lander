Questions:

(We can ask any team member to explain any of the answers below
 in terms of your team's solution).

1) What was the impact of having noisy sensors in your ability to
   determine the state of the craft and ultimately control it 
   properly?
   - Noisy sensors create unstable control decisions because small
     fluctuations in position/velocity/angle can trigger large thrust
     and rotation changes.
   - This leads to oscillation, over-correction, and late braking if we
     directly trust raw measurements.

2) Describe the technique(s) you used to deal with sensor noise
   - We used filtering/smoothing on state variables and rejected outliers
     with consistency checks.
   - We estimate velocities from position deltas and use that estimate
     when direct velocity readings are inconsistent.
   - We normalize and smooth angle changes using shortest-rotation logic.

3) Describe your strategy for dealing with thruster failures
   - We route thrust commands through a robust thruster helper that
     chooses a working thruster if the main thruster fails.
   - We adapt orientation logic based on which thruster is available.
   - Safety override applies stronger emergency thrust when collision risk
     is detected.

4) Describe your strategy for dealing with sensor malfunctions:

   - Position sensors
     Use smoothed history and bounds checks to reject implausible values.
   - Velocity sensors
     Cross-check direct velocity against position-derived velocity estimate.
   - Angle
     Normalize angle and rotate through shortest direction to reduce
     control jitter from noisy readings.
   - Sonar
     Use valid sonar sectors when available and fallback to RangeDist().

   What if you have multiple failures? what could you do if, for
   example both position and velocity sensors became inoperative?
   - If both position and velocity fail, we should rely more heavily on
     angle + range/sonar geometry and conservative descent policies.
   - A practical strategy is to hold near-vertical attitude, cap descent
     speed, avoid lateral motion, and only make small corrective actions.
   - We should also track confidence scores for each sensor and switch
     policies based on confidence.

5) What was the hardest failure type to deal with (i.e. which is
   the component, either sensor or control that makes the lander
   harder to handle?)?
   - Combined failures (especially velocity + position with a thruster
     failure) are currently the hardest because control needs both
     reliable state and sufficient actuation authority.

6) Assume a human pilot was in charge of controlling the craft 
   (i.e. the pilot has control of thrusters and rotation).
   How would you change Safety_Override() so that it prevents
   the pilot from accidentally crashing the lander?
   - Keep pilot controls active by default, but add hard safety envelopes
     (max descent speed, max tilt near ground, min terrain clearance).
   - If pilot commands violate envelopes, clamp or override with a brief
     corrective maneuver and then return control to the pilot.
    
7) Do you think it is reasonable to write such a control function?
   (i.e. a routine that takes control from a human for their
    own safety)
   - Yes, if the override triggers are transparent, bounded, and tested.
   - It should only intervene in clearly unsafe states and should not
     fight normal pilot intent.

8) Should the pilot be aware that this software is present?
   (yes or no, and tell me why you think so!)
   - Yes. The pilot needs to know when and why control can be overridden
     to maintain trust, predictability, and accountability.

9) Would you buy/drive a car that you know has control software
   that will take control from you if it estimates you are
   doing something dangerous?
   - Yes, if there is strong safety evidence, low false positives, and
     clear driver notification when intervention occurs.

10) Can you as an embedded systems designer think of every 
    possible scenario that could go wrong so as to write 
    control software that ALWAYS works?
    - No. We cannot enumerate every real-world scenario, so we must
      design for graceful degradation, robust fail-safes, and continuous
      validation instead of assuming perfect coverage.
